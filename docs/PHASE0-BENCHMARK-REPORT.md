## Key finding: `computeInsightModules` has a real quadratic-ish hot spot at scale

The insight-modules timings above are not a flat, uniformly-scaling cost — they blow
up disproportionately as size grows (28.57 ms → 53.66 ms → 240.52 ms → 6168.12 ms across a 50x
growth in people, i.e. roughly two orders of magnitude more than linear). A CPU profile
(`node --cpu-prof`) taken against the 5,000-person fixture attributes **~82% of all CPU
time inside `computeInsightModules`** to a single module: `bridges()`
(`src/lib/insightModules.js`), the "cut point" family-structure insight. Its own code
comment already documents the complexity honestly — *"Exhaustive but cheap: remove each
person once and BFS their component's remains. O(people × edges) — a few million ops at
1,000 people"* — but that comment's own "cheap" framing does not hold at 5,000: a few
million ops at 1,000 people becomes tens of millions at 5,000 (the cost scales with both
the outer removal loop AND the per-removal BFS over the remaining graph, so it is not a
simple linear multiplier).

This directly matters for the storage/perimeter ADR: **any perimeter or halo feature that
re-triggers a full insight recompute on every viewport/anchor change would inherit this
cost.** The existing code already computes insights once per tree load, not per
interaction, so today's impact is "the insights sheet takes ~5–6s to open the first time
on a 5,000-person tree," not a per-frame cost — but it is the single largest non-payload
number this benchmark found, and worth a scoped follow-up (likely: only run `bridges()`
lazily/on-demand rather than eagerly in the main `computeInsightModules` pass, or cap its
exhaustive removal scan to a bounded neighborhood) independent of whatever the storage ADR
decides — it is a computation-cost problem, not a payload-size problem, and the two need
different fixes.

## Reading these numbers

- All timings are single-run Node measurements on this container's CPU, not a real
  device or browser JS engine — treat them as **relative, order-of-magnitude**
  evidence for where cost concentrates as size grows, not as absolute production
  latency budgets.
- `buildGraph`/`distancesFrom`/`relationLabel`/`findDuplicatePairs`/
  `computeInsightModules` are exactly the functions the running app already calls —
  this harness adds no shims or mocks around them.
- The payload-size numbers are the most directly load-bearing for the storage ADR
  (task after this one): they show where the existing D1 1MiB-per-row ceiling and
  `treeStore.js` core/R2-extra split sit relative to real fixture sizes at this scale.
